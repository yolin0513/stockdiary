# SPEC_整套上限 — 照共用慣例 v3 §5.7，在 STATUS 寫明本 App 的整套上限

> 狀態：已執行（2026-09-21）
> 撰寫：Fable 統籌 Session，2026-09-21。回應你 v3 更新回報的第二點（STATUS 沒有 §5.7 要的上限，而你那一列寫「無」——那是統籌者漏了，你沒有自己加是對的）。docs-only：不 bump、不部署、不跑整套。不急，跟下一個工作一起做即可。

## 要做的事（只動 `docs/STATUS.md`）

1. 在你記「全面檢測怎麼跑」的那一節，加固定的三行（措辭你定，意思要到）：
   - **整套上限：距上次突變整套 10 版，或自上次整套以來新增／改過的突變達 25 條（約一成）。** 超過任一個 → 每版回報最前面用一行講出來，並建議「這一批做完就跑」；沒超過不必每次提。要不要跑仍由 Yolin 決定；這是提醒的門檻，不是禁止多跑。
   - **上次突變整套：日期、版本、條數、結果、耗時。** 照你查得到的填；查不到的欄位寫「無紀錄」，不要推算。
   - **上次全面檢測：日期、版本、結果、總耗時。** 同上。
2. **整套耗時的兩個數字互相矛盾**（同一份 STATUS 一處寫約 3.5 小時、一處寫約 4 小時），而且你回報它們是文件記載值、不是實測。兩處都改成同一句：「約 3.5–4 小時（文件記載，未實測；下次全面檢測時量總秒數與最慢五支並更新這裡）」。不要挑一個數字當真。
3. 「自上次整套以來新增／改過的突變幾條」怎麼數：用你現有的做法即可（你有從 git diff 算受影響突變的機制）；STATUS 寫明是怎麼數的。**這一批不新增腳本、不改 `doctest`**——如果你判斷值得做成自動提示，在回報裡提，另外排。

## 數字的來由（給日後讀到的人）

統籌者訂的，依據是 MealMate 2026-09-19～21 的實測（366 條整套跑出 3 條靜默失效；一次會改變輸出的改版後重跑 191 條，0 條失效），MealMate 取 10 版／40 條（約一成）。StockDiary 234 條，取同樣的比例。你發版比 MealMate 慢、成本／損益數學又凍結，實際上很久才會碰到上限——那沒關係，上限的用途是不讓整套無限期往後推。你認為數字該調，在回報裡講理由。
