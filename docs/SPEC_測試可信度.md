# SPEC_測試可信度 — 讓突變能指定「該紅的是哪一條」、`upgradecheck` 不再被文件 commit 弄紅、補兩個舊洞

> 狀態：已執行（2026-09-23）
> 規劃：Fable 5.1 統籌 Session，2026-09-21。事實依據：你 2026-09-21 全面檢測的回報（實測 1 小時 52 分：28 支 506 秒、突變 234 條 5,609 秒；76 條從未整套跑過的全紅）與 `docs/SPEC_待辦草稿.md` §1、§2（統籌者審過，這一份取代那兩節；§3 已因 B4 結案作廢、§4 仍等 Yolin）。
> **只動 `scripts/`、測試與文件；不動 `js/`、不 bump App 版本、不碰凍結區。** 不需要 Yolin 決定。四項各自獨立 commit。

## 為什麼

全面檢測全紅是好消息，但它同時露出：這個 repo 的突變**只能證明「改壞之後那支測試有紅」，不能證明紅的是它想守的那一條**；而且整套的前置檢查會被我們這幾天一直在做的事（連續的文件 commit）弄紅，擋住整個突變全套。這兩件不修，下次整套的結果一樣要打折看。

## A. 突變條目支援 `expect`（紅的一定要是含這段字的那一條）

- 現況：條目只有 `name／why／file／find／replace／test`，判定是 `ok(r.code !== 0)`。
- 要做的：條目可以多帶一個 `expect`（字串）。帶了的，判定改成「那支測試失敗，**而且失敗的斷言訊息裡有一條含這段字**」；失敗了但沒有任何一條含這段字 → 這條突變判成**不合格**，輸出要分得出「沒紅」與「紅錯地方」兩種。沒帶 `expect` 的照舊。做法可以參考 MealMate `scripts/mutationtest.mjs` v0.36.0 之後的實作（唯讀參考，不要複製它的條目）；你的測試輸出走 `tap.mjs`，怎麼從輸出裡取出失敗的斷言訊息由你定。
- **從這一份起，新增的突變一律要帶 `expect`**；寫進 STATUS 的測試慣例。
- 既有 234 條**不整批補**（MealMate 同一題的結論：補 `expect` 救不了「情境消失」那一類，整批補不划算）。只先補一類：**`file` 指向資料檔或產生出來的檔**（`data/**`、任何 build 產物）的突變——這類最容易「改了資料，結果紅的是『某某檔是最新的』那條，而不是它想守的那條」。先數出有幾條、列進回報，再補。
- 測試（放你認為合適的那一支，建議 `doctest` 或替 `mutationtest` 自己開一小段自我測試）：
  | # | 斷言 | 對照組 | 突變 |
  |---|---|---|---|
  | A1 | 假的測試輸出＋`expect` 命中 → 合格 | 輸出有失敗、但沒有任何一條含 `expect` → 判成「紅錯地方」；完全沒失敗 → 判成「沒紅」| 讓判定忽略 `expect` |
  | A2 | 每一條帶 `expect` 的條目，它的 `expect` 在對應的測試檔原始碼裡找得到（防打錯字，永遠不會命中）| 對照：故意打錯的 `expect` 被抓到 | 讓這個檢查永遠通過 |

## B. `upgradecheck` 的「舊版」基準不要用 `HEAD~1`

- 現況：`OLD_REV` 預設 `HEAD~1`。v0.7.22 之後連續五個 commit 全是文件 → 「舊版」與「新版」的 App 完全相同 → 基準不綠 → **突變全套一條都沒跑**。你這次是把 worktree 切到 `d2e5b7e` 繞過去的。
- 要做的：預設的舊版改成「**最近一個版本號與現在不同的 commit**」（從 `js/version.js` 或等同的版本來源往回找；或等價地，最近一個動到文件與 `CLAUDE.md` 以外檔案、且版本不同的 commit）。找不到（全新的 repo）→ 清楚地報「沒有可比的舊版」並以可辨識的方式略過，**不要靜默通過、也不要紅**。`-- <rev>` 手動指定照舊。
- 原註解裡的教訓（「寫死 commit id 會讓真正要驗的那一跳從來沒測到」）保留，補上這次的教訓。
- 測試：
  | # | 斷言 | 對照組 | 突變 |
  |---|---|---|---|
  | B1 | 挑基準的函式（抽成可單獨呼叫的純函式，餵假的 commit 清單）：最近幾個都是文件 commit → 跳過它們、挑到上一個版本 | 最近一個就是版本 commit → 挑它的前一版；沒有任何舊版 → 回報「沒有可比的舊版」| 把它改回 `HEAD~1` |
  | B2 | 真的在這個 repo 上跑一次：現在（HEAD 是文件 commit 或 v0.7.23）挑到的舊版，版本號確實與現在不同 | 前置：`git log` 裡確實有比現在舊的版本 | — |
- 全面檢測的流程說明（STATUS 那一節）更新：不必再為了 `upgradecheck` 切 worktree 的基準。

## C. 過期的突變與「突變會不會過期」的檢查

- 現況：一條突變過期（長條寬度在 v0.7.22 的 A8 改成 CSS 變數 `--w`，突變的 `find` 沒跟上）——**對應的斷言從 v0.7.22 起沒有被驗證過**。
- 要做的：(1) 修那一條，並確認修完之後它會紅、而且紅在對的斷言上（用 A 的 `expect`）。(2) 你的執行器已經會在 `find` 找不到時判過期——但那要等到整套才跑得到。加一個**秒級**的獨立指令（比照 MealMate 的 `checkmutations`）：不跑任何測試，只檢查每一條的 `find` 在 `file` 裡**剛好出現一次**；納入每版必跑的清單。(3) 這次是怎麼發現它過期的、它過期了多久，寫進 STATUS 的坑。
- 測試：C1 對照組——餵一條 `find` 不存在的假條目 → 被抓到；餵一條出現兩次的 → 被抓到。突變：讓檢查永遠通過。
