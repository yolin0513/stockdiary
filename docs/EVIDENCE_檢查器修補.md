# 檢查器修補的三段證據（EVIDENCE_檢查器修補.md）

> 四家統一檔名（Dispatch 2026-09-24 補充說明（四）第 2 點）。`docs/STATUS.md` 是接手契約，只留摘要並指向這裡；逐件的三段證據寫在這裡，驗收時一次讀完、以後也查得到。
> 對話回報會丟，§5.7 也寫明證據只存在本機等於沒有紀錄——所以證據進 repo。

## 共通做法（每一件都照這個做，下面不再重複）

- **在哪裡跑**：repo 外的暫存複本，commit 之後跑；不碰真的 repo。打網路的一律換成本機假伺服器或錄好的回應（`livecheck` 的「對真的證交所實跑」除外，那是它平常的用法，也在複本裡跑）。
- **修正前怎麼取**：一律從**明確的 commit** 取（逐件寫是哪一個），取出後先斷言**新舊檔案雜湊不同**、而且**舊版裡確實還有舊寫法**（逐件寫檢查了什麼）；不過就中止、不讀輸出。S3–S7 當時寫的是「從 GitHub 追蹤分支取」，當時追蹤分支所指的 commit 已在輸出裡印出，這裡換成明確的雜湊。
- **讀到的輸出是這一次的**：每次跑之前刪掉舊輸出檔；改壞的那一份有沒有被執行到，比雜湊（§5.11 第三層）。
- **擋下的理由要落在錯誤訊息的位置**（補充說明（四）第 1 點）：不數「整份輸出有沒有出現那個字串」——正常輸出本來就可能印出同一個字串。每一個比對理由的地方都另有兩個方向的對照組（只出現在別處 → 不算；出現在錯誤訊息裡 → 算）。
- **比對兩份結果之前，先斷言兩邊都抽到預期的數量**（第 3 點）：「相同」在母體是空的時候恆真。
- **突變的判定**（2026-09-24 起）：要「**只紅對應的那一種**」——紅在 `expect` 之外還有別組一起紅，判「多紅了別組」；本來就會連帶紅的要用 `alsoRed` 明列、`alsoRedWhy` 寫理由（`checkmutations` 擋沒寫的）。

**F8：三支 build 資料變少照樣寫檔（`3cf33ae` 第一版 → `04b205e` 第二版 → 這一輪第三版：補充說明（四）第 5 點）**

> 這是財務資料：`build-dividends` 在一筆都收不進來時，會寫出「0 檔」的 `dividends.json`，App 照常顯示、沒有任何提示。

- **修法**：寫任何檔之前先驗完每一個單位（來源不是陣列、0 筆、欄位逐筆對不上、解析不了、取不到、`build-dividends` 收進來 0 檔、比上一次成功的少一半以上、上一次的輸出壞掉）；有任何一項不過就一個檔都不寫，**每一條理由以單位開頭**。寫檔：先寫 `<輸出檔>.tmp` 再換上；**只清自己寫出的暫存檔**——暫存檔的位置被別的東西佔住（例如同名資料夾）就不動它、照實講；**清理本身失敗也點名留下了哪個檔、不中斷**；這些設計好的停下只印訊息、不印堆疊（沒料到的例外才印）。JLPT、MealMate 都中過的 `ERR_FS_EISDIR`（去刪那個同名資料夾、刪不掉、再丟一次例外、吐堆疊）就是這一格。
- **驗法**（F8 四家統一、照 MealMate 的形狀）：`scripts/buildtest.mjs` 的母體是**逐字寫出的「單位 × 情境」矩陣**，共 **54 格**：日曆（休市日公告）× 5、股利（t187ap45_L）× 5、代號表 6 份來源 × 4 ＋ 3 個市場 × 變少、日曆的「沒有這一年」「新的一年變少」、股利的「後面幾筆改名」「代號全不合格式」「現金股利全空」、三支「上一次的輸出壞掉」各 1、三支「寫檔失敗」各 3（暫存檔的位置被資料夾佔住、輸出檔設成唯讀而換不上去、換不上去而且清理也失敗）。前置斷言確認這幾張表＝單位 × 情境、來源＝腳本裡的 `SOURCES`。
